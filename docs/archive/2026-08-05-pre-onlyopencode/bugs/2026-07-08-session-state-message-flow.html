Agent Workspace 信息传递与状态确认流程

目标是明确：所有 Agent 卡片、Workbench 进度、Task 时间线、Conductor MCP 工具读取的状态，都来自同一个 Session Store 投影。PTY 只触发检查，不直接判断语义状态。动画只消费 attention projection，不创造状态。

一、正常消息传递主链路

从任务发起到 Worker 结果回到 Conductor，再到 UI 展示的完整路径。

二、状态事实分层与唯一投影

写入者只追加事实；统一 reducer 产出一个可见主状态和若干副事实。

reduceSessionState(facts)
Process fact PTY 是否启动、运行、退出。只回答生命周期，不回答语义。

not_started running_process exited

Provider fact Provider 是否正在生成、等待用户输入、需要权限、阻塞。

running waiting_input permission_required

Dispatch fact 每个 assignment 自己的生命周期，不等同于整个 session 状态。

queued delivered failed

Result fact 某个 dispatch 已有可读结果；必须保留 dispatchId/resultId。

result_available result_invalid

Task gate fact 完成声明、review gate、Goal 确认，不从自然语言直接推断。

completion_claim pending_review done

投影原则 对外仍只有一个 AgentRuntimeState，但 sessions[] 同时携带副事实： activeDispatchId、lastResultId、resultCount、unresolvedFailureDispatchId、 attentionHints。UI label 可以显示为 Delivery failed · result available，避免最后一次失败遮掉已有结果。

三、异常路径如何传递

异常不直接变成弹窗；先进入 pendingDecisions，再由 UI 根据规则决定提醒或确认。

exception handling

投递失败 delivery_failed

  • 记录 dispatch.failed，必须带 dispatchId、reason、message。
  • Session 主状态可投影为 delivery_failed。
  • 如果已有历史结果，必须保留 lastResultId 和 result pending decision。
  • UI 展示：Delivery failed · result available，不是只显示失败。

Provider 等用户输入 waiting_input

  • Adapter 读取 provider-native question，而不是解析 TUI 文本。
  • 记录 session.waiting_input，pending decision 带 question/options。
  • UI 对未确认 decision 做短 pulse；选中任务时显示确认面板。

权限请求 permission_required

  • Provider 请求文件写入、命令执行、越权路径、策略例外时进入该状态。
  • 必须弹窗确认；弹窗要显示 actor、action、path/command、risk、允许/拒绝。
  • 确认结果写 permission.resolved，不能只写终端输入。

结果无效 result_invalid

  • Provider turn stop 但没有 answerText，也没有 expected artifact。
  • 记录 compact failure event，并 wake Conductor。
  • UI 不弹窗；显示 blocked/invalid badge，等待 Conductor 选择 retry 或改派。

Provider / PTY 退出 exited

  • PTY exit 是 process fact，不应直接覆盖已有 result fact。
  • 若 active dispatch 无结果，产生 session_exited pending decision。
  • UI 提供重启/重新派发操作；重启前可根据未完成 dispatch 弹确认。

完成声明 completion_claim

  • Conductor 自然语言 “Task complete” 只是 conductor.message。
  • 只有结构化 task.completion_claim 才能进入 review / Goal gate。
  • 最终 done 必须由用户确认或 Review gate 通过后写入。

四、什么时候弹窗确认

弹窗是阻塞式确认，只用于需要人类承担决策或风险的动作。普通状态变化只做 badge / timeline / attention cue。

confirmation policy
触发条件 是否弹窗 原因 确认结果写入哪里
waiting_input 且 provider 给出明确用户选项 是 Conductor 已经无法安全自动决策，需要用户选择路线。 user.intervention + provider 输入；保留 question/options。
permission_required / 越过 ask-before-write 是 涉及写文件、执行命令、权限升级、风险边界。 permission.resolved，并可写 user.intervention。
Conductor 要直接修改 Worker-owned deliverable 是 这是协议例外；必须显示为何不能 route 给 worker、修改范围、review 后续步骤。 user.intervention + 后续 dispatch/review 事件。
重复 delivery_failed 后准备 retry / reset / replace session 条件触发 第一次失败可由 Conductor 自行 retry；连续失败或需要 reset 时要求用户确认。 dispatch.failed 保留历史，确认动作写 user.intervention。
result_available 否 这是正常信息传递，应该 wake Conductor 和 timeline 展示，不打断用户。 results.jsonl、messages.jsonl、pendingDecisions。
Conductor 声明任务完成 是，进入 Goal / Review gate 自然语言不是 done；必须有人或 review gate 确认。 task.completion_claim → review gate → task done。
用户点“停止”正在运行的 PTY 条件触发 如果有 active dispatch 或 provider 正在生成，弹确认；空闲时可直接停止。 session.stopping / session.exited + action event。

五、UI 提醒与动画边界

动画只表达“需要关注”，不参与状态判断，不放大错误状态。

attention projection

可以动画

  • waiting_input：短 pulse 或一次性轻微 shake。
  • permission_required：短 pulse + 明确权限按钮。
  • 只对未确认 pending decision 动画。
  • 选中 Agent 后停止动画，转为静态 attention 样式。

不应该动画

  • delivery_failed 不持续抖动，只用红边和 badge。
  • result_available 不弹窗，只做 ready cue。
  • 已有结果 + 后续失败时，不要只对失败做强提醒；必须显示复合信息。
  • 尊重 prefers-reduced-motion。

建议实现顺序：先修 deriveSessionRuntimeState() 的复合 dispatch 投影，再扩展 sessions[] / pendingDecisions 字段，随后更新 Agent 卡片 label，最后再添加 attention 动画。
